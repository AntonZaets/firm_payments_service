# Functional payment test suite

## Approach

Write HTTP contract tests against `POST /api/v1/payments/bulk`, backed by real PostgreSQL. Use Polyfactory for generated data and pytest fixtures for database setup, cleanup, clients, and assertions.

Payment tests will initially fail because the endpoint is unimplemented. Mark them `payment_contract` and temporarily exclude that marker from default pytest runs. Run them explicitly with:

```bash
docker compose run --build --rm -T app uv run --locked python -m pytest -m payment_contract -o addopts=
```

Keep existing health tests in the default run. Do not implement payment handling or use `xfail`.

## Test list

### PDF example and successful transfers

| Test | Assertions |
|---|---|
| Exact PDF worked example | Seed all three firms exactly; submit the three payments from page 4 unchanged; expect 201. |
| Single payment | Correct debit, credit, internal firm IDs, amount, and description. |
| Multiple distinct recipients | Each recipient receives its amount; payer pays the total. |
| Repeated recipient | Separate payment rows and descriptions; recipient receives the combined credit. |
| Balance equals batch total | Transfer succeeds; payer ends at zero. |
| Exact monetary conversion | Parameterize `"300"`, `"5800.5"`, `"1200.75"`, and `"0.01"`; assert exact integer cents. |
| Negative recipient balance | Accept the transfer, including when the resulting recipient balance remains negative. |
| Repeated HTTP submission | Two submissions produce two transfers and distinct request IDs/audit rows. |
| Limits accepted | Accept exactly 1,000 payments and a description of exactly 1,000 characters. |

The PDF test uses these exact firms:

| ID | Name | UUID | Before, cents | After, cents |
|---|---|---|---:|---:|
| 1 | Pinecrest CPA Group | `3f1c9a2e-7b4d-4c1e-9a55-2d8e6f0b7c41` | 5,000,000 | 3,674,875 |
| 2 | Lopez Bookkeeping | `8b2e4c71-0d3a-4f6e-b1c9-5a7d2e9f4c10` | 50,000 | 170,075 |
| 3 | Nair Tax Services | `e5f18b3c-2a9d-4c07-8e6b-1d4a7f9c3b25` | 200,000 | 1,405,050 |

Its stored payments must be `(payer ID, payee ID, cents)`:
`(1, 3, 625000)`, `(1, 3, 580050)`, `(1, 2, 120075)`, with the PDF descriptions verbatim.

Every success test checks committed state through an independent database connection, total balance conservation, and one audit row per request containing the original parsed JSON and returned request ID. Compare payment rows without assuming generated IDs or query order.

### Validation and business failures

| Test | Expected outcome |
|---|---|
| Insufficient total funds | 422, `INSUFFICIENT_FUNDS`; include a batch where each entry is individually affordable. |
| Zero or negative payer balance | 422, `INSUFFICIENT_FUNDS`, rather than unknown payer. |
| Unknown payer or recipient | 422, `UNKNOWN_FIRM`; include an unknown recipient after a valid entry. |
| Ambiguous UUID mapping | Reject duplicate firm UUID mappings; do not select an arbitrary firm. |
| Empty payments | 422, `EMPTY_PAYMENTS`. |
| Self-payment | 422, `SELF_PAYMENT`; include differently formatted representations of the same UUID. |
| Invalid UUID | Parameterize payer and payee; 422, `INVALID_UUID`. |
| Invalid amount | Parameterize zero, negative, excess decimals, whitespace, exponent notation, nonnumeric strings, and JSON numeric values. |
| Integer overflow | Reject an out-of-range payment, batch total, or resulting recipient balance. |
| Missing fields / incorrect types | Parameterize required fields and body/list/entry types; 422, `INVALID_FIELD` where documented. |
| Malformed JSON | 422, `INVALID_JSON`. |
| Exceeded limits | 1,001 payments or 1,001 description characters; 422, `INVALID_FIELD`. |
| Multiple independent errors | Return multiple available validation errors; no database writes. |

For every rejected request, compare all three tables against a pre-request snapshot, including preexisting payment and audit rows. Assert documented codes and nonempty details without matching exact prose. Where the design does not specify a code, assert rejection and unchanged state only.

### Atomicity and concurrency

| Test | Assertions |
|---|---|
| Payment insertion failure | A test-installed PostgreSQL trigger rejects a later payment insert; expect 500 and complete rollback. |
| Audit insertion failure | A PostgreSQL trigger rejects audit insertion; expect 500 with no balances or payments changed. |
| Concurrent overspending | Two synchronized clients submit individually affordable transfers whose combined total exceeds funds; exactly one succeeds, no overspend or partial state. The other returns 422 or documented 503 if retries exhaust. |
| Shared recipient | Two independent payers concurrently credit one recipient; both succeed, with no lost credit. |
| Firm pays and receives concurrently | Concurrent transfers share a firm in opposite roles; both succeed and balances match both committed transfers. |

Use separate HTTP clients and database connections for concurrent requests, synchronized with a thread barrier. These tests exercise database coordination rather than an in-process shared session. Join workers before cleanup. Check payment/audit counts and conservation after all responses.

## Fixtures and data generation

| Fixture / utility | Responsibility |
|---|---|
| `test_database` — session scope | Create a uniquely named disposable database on the existing PostgreSQL server; create test-owned platform and audit tables; dispose connections and drop it at session end. |
| `db_engine` — session scope | Connect only to the disposable database, with enough connections for concurrent requests. |
| `clean_database` — function scope, autouse for contracts | Clear payments, audit, and firms before and after each test using the test owner; reset identities. Cleanup runs even after assertions fail. |
| `db_connection` — function scope | Provide a separate connection for committed seeding and state inspection; never wrap application requests in an outer test transaction. |
| `client` — function scope | Point application database configuration/engine references at the test database, disable payment authentication, and create `TestClient` with server exceptions converted to HTTP responses. Restore overrides afterward. |
| `client_factory` | Create independent clients for concurrency tests using the same test database. |
| `firm_factory` | Polyfactory dataclass factory with valid UUIDs, names, and bounded integer balances; support explicit overrides and committed insertion. |
| `payment_factory` / `bulk_request_factory` | Polyfactory dataclass factories producing valid payloads linked to seeded firms; explicit overrides control amounts and edge cases. |
| `transfer_case` | Seed payer, recipients, and an unrelated firm; return the corresponding request and starting state. |
| `pdf_example` | Override factory fields with all exact PDF values and return the unchanged sample request. |
| `database_snapshot` | Return a callable reading normalized rows from all three tables. |
| `database_failure` | Install a narrowly targeted failure trigger for payment or audit insertion and remove it in teardown. |

Use standard-library dataclasses as factory models so collection does not depend on nonexistent application schemas. Generate valid baseline data; introduce invalid values explicitly in parameterized tests. Keep expected cents and balances explicit, independent of application conversion logic.

```text
    └── test_payment_concurrency.py    # Independent concurrent requests
```

## Defaults and acceptance

- Provision documented tables in the disposable database; do not alter the platform database or add production migrations. Migration validation is deferred.
- Use PostgreSQL `INTEGER` ranges for platform money columns and the documented audit schema. Do not add a UUID uniqueness constraint that would prevent testing ambiguous mappings.
- JWT verification, explicit serialization-retry injection, operational endpoint expansion, and load testing are deferred.
- Document the test database lifecycle and temporary contract-test command in the design.
- Default checks and existing tests must remain green. The explicit contract run must collect successfully and expose missing behavior through failures; once payment handling exists, all contracts must pass and the temporary default exclusion can be removed.
