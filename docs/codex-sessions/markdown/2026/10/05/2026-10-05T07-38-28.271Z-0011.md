# Implement bulk payments without payment authentication

## Summary

Implement the documented payment API, transactional transfers, audit storage, and payment observability using the existing dependencies and prescribed API → service → repository structure.

Success means all existing non-auth functional contracts pass unchanged, with isolated unit tests covering the implemented behavior. Baseline: 15 tests pass; 64 payment contracts fail because the endpoint is missing.

## Implementation changes

- **API:** Add synchronous `POST /api/v1/payments/bulk`. Capture the original parsed JSON separately from validated schemas. Reuse the existing generated request ID; return HTTP 201 with `{"request_id": "…"}` only after commit.
- **Validation:** Require string UUIDs, string amounts, string descriptions, and a nonempty payment list. Convert validated dollar strings to cents using integer arithmetic. Collect available validation errors and map them to the documented codes and HTTP 422 response shape, including malformed JSON, wrong types, UUID errors, limits, and self-payments.
- **Persistence:** Add internal SQLAlchemy mappings for platform firms/payments and the audit table. Create request-scoped sessions from the current database engine so the existing functional fixtures can substitute their engine. Repositories never commit.
- **Transfer rules:** Resolve every UUID to exactly one firm. Validate stored balances, individual amounts, batch totals, and resulting balances against database integer ranges before writes. Reject insufficient funds, allow exact funds and negative recipient balances, aggregate recipient credits, and preserve each input entry as a separate payment row.
- **Transactions:** Use SERIALIZABLE isolation before any transaction queries. Apply balance changes in ascending internal firm-ID order, insert payments and one audit row, then commit. Roll back all changes on validation or persistence failure.
- **Retries:** Retry only SQLSTATE `40001`, including commit-time failures, using a fresh transaction and renewed reads and validation. Preserve the original body and request ID. Return correlated HTTP 503 with `Retry-After` on exhaustion; return generic correlated HTTP 500 for other database failures without retrying.
- **Schema integration:** Inspect platform column types and description limits through the transaction connection; enforce actual integer widths and any stricter description limit. Unsupported schema types fail safely rather than permitting unsafe writes.

## Configuration, migrations, and observability

- Add validated settings for maximum batch size and description length (both 1,000), total serialization attempts (3), retry delay (50 ms), statement and lock timeouts (60 seconds each), and `Retry-After` (1 second). Apply timeouts transaction-locally on every attempt.
- Add an Alembic revision for `firm_payments_audit` with the documented identity, timestamp, UUID, and JSON columns. Filter autogeneration to service-owned tables so it cannot create, alter, or drop platform tables.
- Document separate migration/runtime credentials and explicit audit INSERT/SELECT grants; runtime credentials must not own the audit table or have UPDATE/DELETE permissions.
- Reuse request logging and HTTP metrics. Add bounded payment-outcome and transaction-failure counters; log payment success after commit. Keep credentials, bodies, descriptions, balances, and SQL parameters out of logs.
- Update README/configuration examples and relevant design documents to describe deferred payment authentication and resolve implementation details: ambiguous UUIDs use `UNKNOWN_FIRM`, money-range violations use `INVALID_AMOUNT`, and invalid stored balance types use `INVALID_FIELD`. Correct the README’s platform-table migration instructions.

## Test plan and acceptance

- Add parameterized unit tests for exact cents conversion, malformed inputs, UUID normalization, limits, multiple errors, and error-response mapping.
- Unit-test transfer rules with a mocked repository/session: duplicate recipients, self-payments, missing/ambiguous firms, insufficient/exact funds, negative recipients, overflow, ordered updates, original audit body, and commit-before-success.
- Unit-test serialization failures during statements and commit, fresh attempts, rollback, exhausted retries, timeout application, and non-retryable/uncertain failures. Verify correlation, generic database responses, and payment metrics.
- Run the unchanged PostgreSQL functional suite covering the worked example, validation, audit fidelity, rollback triggers, repeated submissions, and concurrent transfers.
